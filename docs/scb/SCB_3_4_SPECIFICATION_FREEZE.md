Authority: This document is the sole spec implementation must follow. 1. Exact Transaction Boundary Ordered steps. T = the single atomic unit of work. 1. Resolve active machine OUTSIDE (read) 2. Backup before stop OUTSIDE (external network) 3. Notify backup started OUTSIDE (notify) 4. Collect session metrics OUTSIDE (external HTTP) 5. Provider pre-verify destroyed OUTSIDE (external HTTP) 6. Provider destroyInstance OUTSIDE (external HTTP) 7. Provider verify destroyed OUTSIDE (external HTTP) 8. Close session (W1) OUTSIDE (gpu_sessions UPDATE) status=closed, ended_at, verified_destroyed_at, settlement_status=pending, destroy_reason 9. ───────────── BEGIN TRANSACTION T ───────────── 10. Claim in_progress (W2) INSIDE (gpu_sessions UPDATE) WHERE user_id, status IN (closed,completed), settlement_status IN (settleable) 11. Deduct wallet balance (W3) INSIDE (users UPDATE) 12. Insert wallet ledger (W4) INSIDE (wallet_transactions INSERT) 13. Deduct entitlement (W5) INSIDE (manual_hour_grants OR subscriptions UPDATE with CAS guard, per line) 14. Sync user_plan_inventory (W6) INSIDE (projection upsert) 15. Finalize settlement (W7) INSIDE (gpu_sessions UPDATE) settlement_status='settled', settlement_at, settlement_breakdown WHERE settlement_status='in_progress' ───────────── COMMIT T ───────────── 16. Finalize usage metrics (W8) OUTSIDE (gpu_sessions UPDATE) 17. Clear machine billing fields (W9) OUTSIDE (machines UPDATE) 18. Mark machine destroyed (W10) OUTSIDE (machines UPDATE) 19. Mark subscription offline (W11) OUTSIDE (subscriptions UPDATE) (must be reachable on retry; see §9) 2. Why Each Step Is Inside or Outside Step Placement Reason 1–7 OUTSIDE Reads or external HTTP. External calls must never hold DB locks; verify must precede the close so the lifecycle guard providerDestroyedVerified is satisfied before any write. 8 (W1) OUTSIDE Already idempotent (closeSession returns IGNORED when status=closed; persistSessionRecord is a same-value overwrite on replay). Keeping it outside shrinks T and preserves "session is closed before settlement is attempted." 9 / 15 T boundary Demarcates the atomic financial unit. 10 (W2) INSIDE Claim is the fence marking "settlement in flight." Must commit/abort with the rest of the unit; otherwise a crash leaves a stuck in_progress. 11 (W3) INSIDE Wallet debit is authoritative. Without W4 it is "lost money." 12 (W4) INSIDE Ledger is the durable proof of W3. W3 and W4 must be atomic. 13 (W5) INSIDE Entitlement consumption is authoritative. Must be all-or-nothing with the wallet side; a partial settlement must not debit entitlements while rolling back the wallet. 14 (W6) INSIDE Keeps projection consistent with committed SoR. Convergent if outside too, but inside removes one replay edge case (see §3). 15 (W7) INSIDE (last) Commit marker. Its visibility implies all financial writes are durable. Must be the final write of T. 16 (W8) OUTSIDE Pure overwrite of duration_seconds, vram_avg_pct, output_count, output_summary. Re-running yields identical values. Not financial. 17 (W9) OUTSIDE Idempotent null overwrite of machine billing fields. Projection cleanup. 18 (W10) OUTSIDE Mirror of session SoR onto machine row. Idempotent. 19 (W11) OUTSIDE Idempotent projection. Must be made retry-reachable (§9). 3. syncUserPlanInventory — Inside or After Commit? A. Inside transaction. Justification: It is a re-derivation from subscriptions.hours_used / manual_hour_grants.hours_used (both written by W5 inside T). Placing it inside T guarantees any observer of settlement_status='settled' also sees a consistent user_plan_inventory. It only upserts rows for the single user (confirmed in user-plan-inventory.js), so the lock surface is bounded to that user's rows — same user T already serializes via W2/W3/W5. After-commit placement is acceptable in principle (the projection is convergent), but it leaves a window where settled is visible and user_plan_inventory is stale. Inside T eliminates that window at negligible cost. Recommendation: A — inside T. 4. incrementHoursUsedCas — Keep CAS or Switch to Plain UPDATE Under Row Locking? Keep incrementHoursUsedCas inside T. Do not replace with a plain UPDATE … SET hours_used = hours_used + ? under row locking. Reasons: The codebase has no pg client and no raw SQL surface (only @supabase/supabase-js v2 / PostgREST). PostgREST PATCH accepts only literal values; it cannot evaluate hours_used + ? server-side. A plain atomic increment is therefore not expressible in the current interface regardless of T. Inside T, the row is already protected by the transaction's isolation; CAS adds a second layer of defence against concurrent writers that bypass T (legacy paths, manual admin, reconciliation quirks). Removing it would widen the trust surface. CAS converges quickly at current settlement volumes; its retry cost is negligible inside T. If SCB 3.4 later adopts a pg client (see §5), CAS may then be reconsidered. Until then, CAS stays. Note: CAS guards concurrency, not replay. Replay safety comes from T's atomicity, not from CAS. A rolled-back T leaves hours_used untouched; replay re-enters T from pending/failed and runs W5 exactly once. 5. Implementation Mechanism — Supabase RPC, pg, or Other? Recommendation: Supabase RPC (single PostgREST function). Why one approach, and why this one: T spans 5 distinct tables (gpu_sessions, users, wallet_transactions, manual_hour_grants/subscriptions, user_plan_inventory) with conditional guards. PostgREST PATCH cannot group these into one atomic call. The only way to make them atomic through the existing Supabase interface is to push the unit of work into a single server-side function invoked via supabaseAdmin.rpc(...). A pg client bound to DATABASE_URL would also work and would give full SQL control, but it introduces a new dependency, a new connection pool, a new auth path, and a parallel DB surface that bypasses PostgREST's RLS and audit hooks. That is a larger architectural change than SCB 3.4 warrants. "Another mechanism" (e.g., client-side orchestration with compensating writes) does not provide true atomicity and is the status quo SCB 3.4 is intended to retire. RPC wins because it keeps the existing @supabase/supabase-js surface as the only DB client, requires no new dependency, runs server-side where the transaction is a native Postgres BEGIN…COMMIT, and can accept a typed payload (sessionId, userId, providerDestroyedVerified, allocation/breakdown) prepared by the existing JS domain logic. Constraint: the RPC must be a pure server-side executor of the W2–W7 sequence; all eligibility, allocation, and breakdown computation stays in the JS domain (settlement-core.js). The RPC receives the prepared breakdown and lines, applies them under one transaction, and returns the SettlementResult shape already consumed by the pipeline. 6. Replay / Idempotency Boundary After SCB 3.4 The transaction T is the replay boundary. Pre-T (steps 1–8): individually idempotent or external. Replay re-runs them safely; closeSession returns IGNORED, verify is a read, destroy is a no-op on an already-destroyed instance. T (steps 9–15): atomic. A crash during T leaves no committed state. Replay re-enters from settlement_status IN (pending, failed) (both in SETTLEABLE_SETTLEMENT_STATUSES), re-claims, and re-runs W3–W7 exactly once. A committed T leaves settlement_status='settled'; replay returns IDEMPOTENT without re-running financial writes. Post-T (steps 16–19): individually idempotent overwrites / projections. Replay converges. The wallet-ledger lookup by description (W4) is retained as defence in depth against duplicate T invocations from upstream bugs, but is no longer the primary idempotency mechanism. 7. Crash Windows That Disappear After SCB 3.4 Window Current failure Resolved by Crash after W2 (claim) Stuck in_progress, no recovery T aborts → no in_progress visible Crash after W3 (debit) Lost money (debit, no ledger) W3+W4 atomic in T Crash after W4 (ledger) Double charge on forced retry T atomic; W3+W4 commit together or not at all Crash after W5 (entitlement) Double entitlement deduction on retry T atomic; rolled-back T leaves hours_used untouched Crash after W6 (projection) Stuck in_progress + stale projection T atomic; W6 commits with W7 or rolls back with them 8. Crash Windows That Remain After SCB 3.4 Window Failure Status Crash after W1, before T Session closed + pending, machine still running in DB Already safe. Replay re-enters pipeline; close is idempotent; T runs cleanly. Crash after W7 (COMMIT), before W8 Settled, no usage stats Safe. Replay returns IDEMPOTENT; W8 re-runs (overwrite). Crash after W8, before W9 Stats written, machine still has billing fields Safe. Idempotent null overwrite. Crash after W9, before W10 Billing cleared, machine still running Safe. resolveActiveMachine still finds it; pipeline converges. Crash after W10, before W11 Machine destroyed, subscription stuck online UNRESOLVED by T. Pipeline early-returns ALREADY_DESTROYED and skips W11. Must be fixed independently (§9). 9. Remaining Known Limitations After SCB 3.4 W11 reachability. markSubscriptionOffline is skipped on the ALREADY_DESTROYED early-return. SCB 3.4 must either make W11 reachable on retry or move subscription offline marking to reconciliation. Independent of T but in scope of the same release. Wallet ledger description collisions. Two sessions of identical duration on the same plan for the same user produce the same description and would collide on the W4 lookup. Pre-existing; not introduced by SCB 3.4; not solved by T. Flag for future hardening (e.g., include sessionId in the unique key). No in_progress lease. T removes the stuck-in_progress window for crashes, but a long-running T (GC pause, network stall between PostgREST calls if T is ever emulated rather than server-side) could still expose a brief in_progress. Reconciliation's detectSettlementDrifts must continue to treat aged in_progress as drift and force RETRY_SETTLEMENT. The audit strongly recommends T be a single server-side RPC so no such mid-T gap exists. Concurrency model unchanged per user. T serializes settlements for a given user via row locks on users, gpu_sessions, and entitlement rows. This is acceptable at current volume but is the throughput ceiling for future scaling. Implementation prerequisite. SCB 3.4 cannot be implemented with @supabase/supabase-js v2 alone. A PostgREST RPC is required (§5). Selecting/authoring that RPC is the first implementation step and is out of scope of this specification. Reconciliation paths unchanged. repairOrphanSession, repairViaDestroyPipeline, and repairSettlementDrift keep their current shapes; they simply benefit from T when they re-enter settleSession. No reconciliation rewrite is mandated by SCB 3.4. CAS remains. Per §4, incrementHoursUsedCas is kept inside T. If a future refactor adopts a pg client, CAS may be revisited; until then it stays as concurrency defence in depth. External calls remain outside T by design. A hung provider will still stall the pipeline at steps 5–7. SCB 3.4 does not change provider-call timeout or retry policy. 10.
